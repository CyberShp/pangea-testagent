# Testagent 任务 Skill 编写助手

把用户提供的操作知识整理为可导入的 Skill。内部命令、路径、脚本留在用户工作区，不请求上传到外部服务。修改已有 Skill 时保留业务意图，增加版本号，不重新发明操作流程。

先读取 [框架约定](references/contract.md)。生成的文件夹包含 `skill.json`、`SKILL.md`、`contract.json`，按需加入脚本及参考文件。没有任务约定的普通 Skill 可以导入，但正式环境配置优先补齐结构化约定。

## 设计重点

- 按实际目标声明设备角色；账号密码只使用设备库，不放进文件、参数或脚本。
- 启动前可确定的参数写入 JSON Schema，现场探测后才能确定的信息用 `ask` 获取。
- 关键操作由业务作者声明，包含影响说明及关联步骤。操作时必须传入相应 `action_id`，不能只在说明里写“请确认”。
- 必要步骤和完成检查覆盖真实生效条件。可由返回值确定的检查提供 `assertion`；其余检查引用实际工具结果，注明 AI 判断依据。
- 保持诊断视图的同一 `session_id`；给出明确提示符，不把静默或断连当成成功。
- 失败立即结束；预期重启可等待恢复，但不能因失败反复重试。恢复方法独立说明，未经用户授权不执行。
- 用户执行中调整要求时，重新评估尚未执行部分；不要自动撤销已经完成的操作。
- 配套脚本在 Linux 执行，长操作由框架跟踪进程组。不要脱离框架自启守护进程；确有必要时明确停止与验证方法。

## 校验与交付

对生成目录执行：

```text
python scripts/check_skill.py <任务Skill目录> --output <输出.zip>
```

校验脚本调用本机已运行的 testagent 校验器，与网页导入使用同一规则；仅检验文件和约定，不操作设备。服务未启动时，先按用户现有安装方式启动本地 testagent。不要另建一套宽松规则绕过错误。

交付目录和 ZIP，说明角色、输入、关键操作及验收条件。校验通过只代表格式与引用一致，不代表内部命令或业务效果已经验证。没有真实环境证据时如实说明，不编造执行日志。
